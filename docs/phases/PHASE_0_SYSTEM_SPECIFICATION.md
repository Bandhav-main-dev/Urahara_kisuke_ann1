# REIŌ — Urahara Kisuke ANN #001

## Phase 0 — System Specification

**Project:** REIŌ
**War Threat:** #001
**Character:** Kisuke Urahara
**Phase:** 0 — System Specification

---

## 1. Project Objective

REIŌ Urahara ANN #001 is a computational cognitive system inspired by
observable and documented Urahara behavior.

The project does not claim literal recreation of a fictional brain or
private fictional thoughts.

The computational target includes:

- analysis
- investigation
- experimentation
- problem decomposition
- hypothesis generation
- strategic planning
- resource utilization
- invention
- adaptation
- contingency planning
- capability composition
- learning from outcomes

---

## 2. Same-Brain Principle

Normal Urahara and WT Urahara represent the same underlying cognitive
system.

They share:

- cognitive core
- memory
- knowledge
- experiences
- inventions
- validated lessons
- learning history

WT is not a second brain and does not receive an intelligence multiplier.

---

## 3. Normal Urahara

Normal Urahara uses the baseline capability-access policy.

The baseline system can:

- analyze situations
- inspect systems
- generate hypotheses
- plan
- experiment
- use validated inventions
- use validated Benihime capabilities
- learn from outcomes
- adapt to changing situations

The baseline profile has a restricted active capability envelope.

---

## 4. WT Urahara

WT means War Threat Urahara.

WT does not mean increased intelligence.

WT uses the same cognitive core and shared memory while allowing an
expanded capability envelope.

WT may:

- access a broader set of validated inventions
- deploy more capabilities in one situation
- combine compatible inventions
- combine validated capabilities
- use a broader tool set
- use more extensive contingencies
- adapt capability combinations
- use environmental resources
- deploy capabilities unavailable to the baseline active policy

All capability requirements, limitations, risks, costs and validation
rules remain active.

---

## 5. Shared Memory

Both profiles use the same memory.

Memory categories:

- working memory
- semantic memory
- episodic memory
- procedural memory
- experimental memory
- strategic memory
- capability memory

A validated discovery made through either profile enters shared memory.

---

## 6. Evidence Classes

Every important record must be classified as one of:

### CANON

Directly supported by an accepted source.

### RECONSTRUCTED

A computational interpretation derived from documented observations.

### SYNTHETIC

A hypothetical, simulated or generated scenario.

Synthetic material must not automatically become canon knowledge.

---

## 7. Cognitive Episode

A cognitive episode should contain:

- situation
- objective
- environment
- known information
- unknown information
- constraints
- available resources
- possible actions
- observed action
- observable evidence
- outcome
- adaptation
- lesson
- source/evidence references

---

## 8. Problem-Solving Engine

The system must distinguish symptoms from possible root causes.

Conceptual flow:

```text
Situation
  -> Symptoms
  -> Factors
  -> Relationships
  -> Root-cause hypotheses
  -> Experiments / information gathering
  -> Decision
  -> Action
  -> Outcome
  -> Learning
```

---

## 9. Problem Graph

Supported relationship types include:

- causes
- contributes_to
- depends_on
- enables
- prevents
- conflicts_with
- correlates_with
- precedes
- follows
- amplifies
- mitigates

---

## 10. Virtual Laboratory

The virtual laboratory supports controlled experimentation.

```text
Hypothesis
  -> Experiment Design
  -> Simulation
  -> Experiment
  -> Result
  -> Evaluation
  -> Knowledge / Strategy Update
```

Experiments must preserve:

- hypothesis
- assumptions
- inputs
- tools
- expected result
- actual result
- failure conditions
- uncertainty
- conclusion
- follow-up

---

## 11. V-1 System Improvement Environment

The system will receive intentionally imperfect systems.

Conceptual process:

```text
SYSTEM V-1
  -> Inspect
  -> Identify symptoms
  -> Analyze factors
  -> Build problem graph
  -> Generate hypotheses
  -> Select experiment/action
  -> Create improved version
  -> Measure actual improvement
```

The system may progress through multiple versions:

```text
V-1 -> V-0.8 -> V-0.5 -> V-0.2 -> V1
```

---

## 12. Reward and Penalty

Reward should primarily reflect measurable improvement and useful
problem-solving behavior.

Potential positive signals:

- system improvement
- root-cause accuracy
- useful evidence gathering
- useful experiments
- resource efficiency
- successful adaptation
- useful invention
- successful capability composition

Potential penalties:

- system regression
- ignoring important factors
- unsupported assumptions
- unnecessary modifications
- uncontrolled experimentation
- repeated failed strategies without adaptation
- fabrication
- false certainty

A failed experiment is not automatically a bad learning event.

A well-designed experiment that efficiently disproves a hypothesis can
still provide positive learning value.

---

## 13. Combat Environment

Combat simulation may contain:

- opponent
- environment
- known abilities
- unknown abilities
- observed behavior
- distance
- resources
- inventions
- Benihime capabilities
- allies
- constraints
- time pressure
- possible actions

The system must select actions according to the current situation.

It must not simply default to the strongest available attack.

---

## 14. User Situation Analysis

The system should be able to analyze a situation described by the user.

The situation model may contain:

- objective
- current problem
- environment
- known facts
- unknowns
- constraints
- available resources
- recent changes
- risks
- success criteria

The response should distinguish facts, assumptions, uncertainties,
possible causes, options, risks and expected outcomes.

---

## 15. Invention System

An invention record should contain:

- purpose
- mechanism
- requirements
- resources
- limitations
- risks
- applications
- failures
- compatible capabilities
- known combinations
- experimental combinations
- validation
- provenance

Conceptual process:

```text
Problem
  -> Requirements
  -> Existing capabilities
  -> Capability gap
  -> Design
  -> Experiment
  -> Evaluation
  -> Modification
  -> Validation
  -> Reusable invention
```

---

## 16. Benihime System

Benihime is represented as a capability/tool interface.

Each capability should track:

- name
- category
- documented effect
- activation conditions
- requirements
- limitations
- resource cost
- risk
- known applications
- compatible capabilities
- evidence
- validation status

Capability classes:

- CANON
- DERIVED
- SYNTHETIC

---

## 17. Learning Architecture

The intended learning loop is:

```text
Situation
  -> Observation
  -> Hypothesis
  -> Decision
  -> Action
  -> Outcome
  -> Reward / Penalty
  -> Explanation
  -> Learning
  -> Shared Memory
```

Reinforcement learning should initially operate inside controlled
simulation environments.

---

## 18. Continual Learning

Important learning updates must preserve:

- previous state
- new state
- evidence
- reason for change
- confidence
- validation status
- rollback information

The system must not arbitrarily rewrite its knowledge after every
interaction.

---

## 19. Training Data Principle

Data is not automatically training data.

```text
Source
  -> Raw evidence
  -> Structured record
  -> Validation
  -> Cognitive / capability representation
  -> Training candidate
  -> Approved training data
  -> ANN #001
```
